\begin{abstract}

Commercial service robots often ship as closed Android-\ros{} systems: no public SDK, no message schemas, and mandatory vendor cloud services, which prevents customization of reception flows, guided tours, and conversational assistants.
This paper's primary contribution is a \emph{reproducible, non-destructive reverse-engineering methodology} for such closed platforms, built around four testable hypotheses (H1--H4) about where the true protocol surface lives and how to verify it without vendor cooperation.
We validate the methodology end-to-end on a single case study, \cybel{}, an open edge platform reconstructed from the CIOT TY1251D-03195 reception robot, a dual-processor system combining a \ros{} navigation chassis and an Android~7.1 head, without manufacturer documentation or support.
The seven-phase pipeline combines network mapping, \rosbridge{}/\rosapi{} introspection, static APK analysis (JADX)~\cite{cybel_architecture}, passive MQTT observation, and field validation of \textbf{H4}: a successful \rosbridge{} transport acknowledgment does not guarantee motor execution.
We document reconstructed teleoperation (\texttt{/cmd\_vel\_mux/input/teleop}), autonomous navigation (\texttt{/navi\_goal} vs.\ POI chain \texttt{/tag\_manager/navi}), and an edge conversational layer (local knowledge engine, Android TTS bridge, guided-tour orchestration) offered as an open alternative to the vendor welcome application.
Runtime testing falsified the expected advantage of named-POI navigation (H3 rejected: \texttt{/tag\_manager/navi} non-functional on this firmware), making H3's rejection a finding in itself and coordinate-based \texttt{/navi\_goal} the confirmed navigation path.
We report a feature-level comparison against the vendor application and quantitative reverse-engineering effort metrics (APKs analyzed, topics/services discovered, elapsed time), in addition to field indicators (${<}100$\,ms local API latency, ${\sim}90\%$ \rosbridge{} session reliability).
We discuss which parts of the methodology generalize to other closed Android-\ros{} robots and which remain vendor-specific.

\end{abstract}

\section{Introduction}
%==============================================================================

Mobile service robots ship as closed Android--\ros{} stacks: no public SDK, no message schemas, mandatory vendor cloud blocking research customisation and locking owners to a single supplier for the hardware's lifetime.

\textbf{Problem.} Three structural obstacles compound reverse engineering: (i)~the chassis and Android head are independent computing environments bridged by an undocumented transport, so no single vantage point (network capture, APK alone) reveals the full command surface; (ii)~locked shells and brute-force lockout make white-box access unavailable; (iii)~a message \emph{accepted} at the software layer may not be \emph{executed} by the actuators, invalidating naive protocol fuzzing.
Prior work addresses Android APK analysis~\cite{enck2014taintdroid} or network protocol RE~\cite{comparetti2009prospex} separately; neither targets the chassis/Android/cloud triad of service robots.

\textbf{Research question.} \emph{Can a non-destructive methodology reconstruct a closed Android-\ros{} robot's command surface with no documentation, and to what extent can the resulting platform reach feature parity with the vendor application?}
We test four empirical hypotheses:

\begin{itemize}[leftmargin=1.3em]
\item \textbf{H1 (APK-as-spec):} vendor APK static analysis (JADX) yields the wire-protocol schemas actually used by the chassis.
\item \textbf{H2 (MQTT-as-command):} the exposed MQTT broker can issue motion commands, as \rosbridge{} does.
\item \textbf{H3 (POI reuse):} vendor Deployment Tool POIs yield higher navigation reliability than independently reconstructed coordinates.
\item \textbf{H4 (transport $\neq$ execution):} a \rosbridge{} acknowledgment does not guarantee chassis execution.
\end{itemize}

Section~\ref{sec:re} shows H1 and H4 \emph{confirmed}; H2 and H3 \emph{rejected} each mechanistically explained. H3's rejection (\texttt{/tag\_manager/navi}, documented in the APK, is non-functional at runtime) is itself a methodological finding.

\textbf{Contributions.}
\begin{enumerate}[label=\textbf{C\arabic*.},leftmargin=1.4em]
\item A seven-phase, non-destructive RE \emph{methodology} for closed Android--\ros{} robots, built on triangulation (network trace $\times$ \rosapi{} $\times$ APK $\times$ field telemetry) and four falsifiable hypotheses.
\item Protocol reconstruction for the CIOT TY1251D-03195: teleop, navigation, and telemetry via \rosbridge{} (Section~\ref{sec:proto}).
\item \cybel{}: edge-first SDK with \texttt{MockRobot}/\texttt{RealRobot} backends, PC/Termux servers, autonomous kiosk (Section~\ref{sec:arch}).
\item TTS channel discovery via a minimal Android broadcast bridge, after \ros{}, HTTP, and MQTT were falsified (Section~\ref{sec:arch}).
\item Feature comparison, RE effort metrics, and generalization analysis for other closed platforms (Sections~\ref{sec:eval}--\ref{sec:discussion}).
\end{enumerate}

LLM-based conversational reasoning is architected (Section~\ref{sec:conv}) but not yet evaluated; artifacts are open~\cite{cybel2026}.

\section{Related Work}
\label{sec:relwork}
%==============================================================================

\subsection{Reverse engineering of Android applications}
Static and dynamic analysis of Android applications has been studied extensively for security auditing, notably information-flow tracking of installed apps~\cite{enck2014taintdroid}.
That line of work targets \emph{data exfiltration} inside a single app; our setting instead uses APK decompilation (JADX~\cite{jadx}) as a way to recover an \emph{inter-process wire protocol} between an Android head and a separate \ros{} chassis, which is not the object of prior Android security literature.

\subsection{ROSbridge and robotics middleware interoperability}
\rosbridge{} was introduced to let non-\ros{} clients (web browsers, mobile apps) interact with a \ros{} graph over a JSON/WebSocket transport~\cite{crick2012rosbridge,rosbridge_suite}, and is normally deployed \emph{by} the system integrator who controls the \ros{} graph.
Our situation is the inverse: \rosbridge{} is deployed by the vendor and we approach it as an \emph{unknown} client would, without access to the underlying node graph or message definitions, which is closer in spirit to black-box protocol reverse engineering~\cite{comparetti2009prospex} than to conventional \rosbridge{} integration.

\subsection{Vendor lock-in and platform openness}
The tension between proprietary and open platform strategies in commercial hardware/software products has long been studied in the innovation-management literature~\cite{west2003open}; service robotics reproduces this tension at the level of a single physical product rather than an industry platform.
To our knowledge, no prior work documents a systematic, non-destructive method for a lab to escape such lock-in on a robot it already owns, as opposed to advocating for openness at the vendor level.

\subsection{Edge and cloud robotics}
Cloud robotics offloads perception and planning to remote servers~\cite{kehoe2015cloud}; our constraint is the opposite: the robot's own Wi-Fi network offers no guaranteed Internet path, so every capability, including speech synthesis, must run at the edge. This motivates the edge-first architecture of Section~\ref{sec:arch} and distinguishes our setting from cloud-robotics deployments that assume reliable connectivity.

\subsection{LLM-based conversational and embodied agents}
Recent work grounds large language models in robot affordances for task planning~\cite{ahn2022saycan} and in multimodal embodied observations~\cite{driess2023paleme}. 
These systems assume an already-open action API. 
Our conversational layer (Section~\ref{sec:conv}) is deliberately designed as the \emph{prerequisite} such systems require on a closed robot: a validated, documented set of navigation and speech primitives that an LLM backend can call without itself rediscovering \rosbridge{} or the TTS channel.

\subsection{Positioning}
Related work treats Android security, \rosbridge{} integration, platform openness, edge robotics, and LLM grounding as separate concerns, each assuming the underlying interface is already known or already open. 
This paper's contribution is the missing piece: a methodology to \emph{establish} that interface non-destructively when it is neither known nor open, together with a case study showing the resulting platform can host each of the concerns above (edge deployment, conversational grounding) once the interface is recovered.

\section{Reverse Engineering Methodology}
\label{sec:re}
%==============================================================================

This section is the core of the paper: it presents the methodology as a set of falsifiable hypotheses tested through a seven-phase pipeline, and explains \emph{why} each difficulty encountered is structural to closed Android--\ros{} robots rather than incidental to this particular unit.

\subsection{Guiding principles}

\begin{enumerate}[label=\textbf{P\arabic*.},leftmargin=1.4em]
\item Observe before publishing (passive MQTT/\rosbridge{} first) minimizes risk of damaging an undocumented, unowned-source system before its behavior is understood.
\item Verify real effects, not transport acknowledgments rule \textbf{H4}: after a teleop publish, \texttt{/robot\_pose} must change before the command is considered validated.
\item Triangulate independent sources of evidence: network traces, \rosapi{} introspection, decompiled APK, and field logs. A hypothesis is only accepted when at least two independent sources agree.
\item Remain non-destructive: no firmware flash, no chassis root, no persistent modification of vendor partitions. This is both an ethical commitment (Section~\ref{sec:discussion}) and a practical one: destructive access on a single loaned/owned unit is not reproducible if it bricks the robot.
\item Mock-first development: every SDK feature is built and unit-tested against a \texttt{MockRobot} before being exercised against \texttt{RealRobot}, decoupling software defects from hardware/protocol uncertainty.
\end{enumerate}

\subsection{Hypotheses and their resolution}
\label{sec:hypotheses}

\begin{itemize}[leftmargin=1.3em]
\item \textbf{H1 (APK-as-spec) - CONFIRMED.} Every \rosbridge{} topic and service name later confirmed on the wire (Section~\ref{sec:proto}) was first located inside \texttt{selfchassislibrary} via JADX. \emph{Why it holds:} the vendor's own Android app must itself speak the true protocol to control the chassis, so its compiled code is a lower bound on the real command surface, unlike documentation which may be aspirational or outdated.
\item \textbf{H2 (MQTT-as-command-channel) - REJECTED.} Passive MQTT observation (wildcard subscription \texttt{\#}, multiple sessions, 1 topic logged: \texttt{test\_mul}, odometry only) showed only odometry and status telemetry; no motion command reproducibly changed robot state when replayed on MQTT. \emph{Why it fails:} JADX audit of \texttt{selfchassislibrary} shows the MQTT client is wired exclusively to telemetry publishers on the chassis side; the command path is implemented only over the \rosbridge{} WebSocket, so MQTT is architecturally read-only from this robot's perspective. This is the diagnostic value of a rejected hypothesis: it saved further engineering effort on a channel that could never work, and it is documented here so future integrators of the \emph{same vendor family} do not repeat the exploration.
\item \textbf{H3 (POI reuse) - REJECTED.} Runtime testing (5~trials each, Section~\ref{sec:hybrid}) showed S3 via \texttt{/tag\_manager/navi} triggered \emph{zero} confirmed navigations (0/5); two apparent successes at $0.5$\,s and $0.6$\,s were stale \texttt{nav\_status=603} reads, not navigation completions. S1 via \texttt{/navi\_goal} achieved $80\%$ (4/5) with mean arrival time $3.5$\,s. \emph{Why it fails:} the service \texttt{/tag\_manager/navi}, present in the compiled APK (\texttt{SelfChassis.\allowbreak{}send\-Move\-By\-Marker\-Name}), is not implemented as a navigation trigger on the deployed firmware. This is exactly the failure H4 anticipates: APK-level presence does not guarantee runtime execution.
\item \textbf{H4 (transport $\neq$ execution) - CONFIRMED, and central to the methodology.} \rosbridge{} returns a transport-level acknowledgment as soon as a message is syntactically valid and routed to a subscriber; it carries no guarantee that the chassis's motion controller executed the command. \emph{Why it holds:} \rosbridge{} sits above \ros{}'s publish/subscribe layer, which itself is decoupled from the safety and motor-control layer on the chassis (e.g.\ manual-mode gating, Section~\ref{sec:proto}); an ack only certifies the first hop. \emph{Consequence:} every validation step in this paper checks \texttt{/robot\_pose} or an equivalent status topic, never the \rosbridge{} response alone.
\end{itemize}

\subsection{Difficulties and why they occur}
\label{sec:re-difficulties}

The following difficulties are structural properties of closed Android--\ros{} service robots, not idiosyncrasies of this unit; we make the mechanism explicit for each so the observation transfers to other robots.

\textbf{Why H4 (transport $\neq$ execution) had to be formulated.} \rosbridge{} is a generic message router; it acknowledges anything that parses as a valid \ros{} message on an advertised topic, regardless of whether any node downstream actually consumes it meaningfully. On this chassis, a manual-mode safety gate (\texttt{control\_state==30}, Section~\ref{sec:proto}) silently drops teleop commands published before the gate is set, while \rosbridge{} still reports success. Any closed \ros{} robot with a safety or mode-gating layer between the message bus and actuation will reproduce this failure mode.

\textbf{Why \rosbridge{} responds without motion.} Same mechanism as above, applied specifically to the WebSocket path: the JSON-RPC style response in \rosbridge{}'s protocol confirms message delivery to the \ros{} graph, not physical execution, because \rosbridge{} has no visibility past the topic it published to.

\textbf{Why MQTT was a plausible but false lead (H2).} The chassis exposes an MQTT broker on port~1883, and MQTT is a common command-and-telemetry bus in commercial IoT/robotics stacks, making it a reasonable first hypothesis. JADX audit later showed the vendor uses MQTT purely as a one-way telemetry export (for fleet dashboards), with all control logic hard-wired to \rosbridge{}; without that audit, this would have appeared as an intermittent, unexplained non-responsiveness rather than a structurally closed channel.

\textbf{Why multiple IPs appear for what looks like one robot.} The Android head and the \ros{} chassis are two independent Linux network stacks bridged by an internal Ethernet link (Fig.~\ref{fig:network}), and the head additionally joins the lab Wi-Fi for deployment. A robot marketed and documented as a single product is, at the network layer, at least two hosts; conflating the head's DHCP address with the chassis's static address is the single most common operator error we observed and is why we document all three segments explicitly rather than a single "robot IP."

\textbf{Why TTS was inaccessible from every standard channel.} The vendor's speech pipeline is implemented entirely inside the Android application layer (opaque IPC to a bundled Iflytek TTS engine), with no bridge exposed back down to \ros{}, HTTP, or MQTT (Table~\ref{tab:tts}); speech was never designed to be a robot-level capability, only an application-level one. This explains why exhaustive protocol-level search (phases 2--3) could not find it, and why the eventual fix (Section~\ref{sec:arch}) operates at the Android application layer instead.

\section{\rosbridge{} Protocol Reconstruction}
\label{sec:proto}
%==============================================================================

\subsection{Transport and client}

\rosbridge{} v2 over WebSocket TCP~9090~\cite{crick2012rosbridge,rosbridge_suite}; JSON operations \texttt{subscribe}, \texttt{publish}, \texttt{advertise}, \texttt{call\_service}.
Our \texttt{RosbridgeClient} (transport module of the \cybel{} SDK) uses three connection retries (20\,s timeout), 20\,s ping keepalive, and automatic reconnect.

\subsection{Teleoperation}

Manufacturer-confirmed topic:
\begin{center}
\texttt{/cmd\_vel\_mux/input/teleop} \quad (\texttt{geometry\_msgs/Twist})
\end{center}
Sequence: \texttt{advertise} then periodic \texttt{publish} (${\sim}10$\,Hz).
Sentrymove ramps linear velocity $\pm 0.025$/100\,ms with $\omega_z \times 0.8$ scaling.

\textbf{Gap E1:} early \cybel{} builds blocked teleop unless manual mode was active (\texttt{control\_state==30}); Sentrymove does not require this step because it always sets the mode implicitly on session start a vendor convention discoverable only via APK audit (H1), not via wire traffic alone.
\textbf{Fix:} auto-enable manual mode on first \texttt{move()}.

\subsection{Autonomous navigation}

Two modes coexist on the chassis:

\begin{table}[!t]
\caption{Navigation modes and prerequisites}
\label{tab:nav}
\centering
\scriptsize
\begin{tabular}{@{}lll@{}}
\toprule
\textbf{Mode} & \textbf{Mechanism} & \textbf{Gate} \\
\midrule
Coordinates (S1) & \texttt{/navi\_goal} & loc.\ ${\geq}60\%$, status 601 \\
Named POI (S3) & \texttt{/tag\_manager/navi} $\rightarrow$ \texttt{/poi} & POI in map \\
\bottomrule
\end{tabular}

\texttt{nav\_status} codes gate \cybel{} commands: 600 not localized, 601 ready, 602 navigating, 603 arrived, 604 error.
Cancellation chain: \texttt{/move\_base/cancel}, \texttt{/path\_follower/cancel}, \texttt{/poi\{command:stop\}}, zero velocity on mux.

\subsection{Telemetry throttling}

Subscriptions use \texttt{throttle\_rate} (ms): \texttt{/robot\_pose} 200 (${\sim}5$\,Hz), \texttt{/navi\_status} 500, LiDAR \texttt{/scan\_filter} 100 limiting \rosbridge{} saturation on constrained Wi-Fi.

\textbf{Application:} a FastAPI development server on PC (port~8000); a lightweight Starlette-based standalone server on Termux (port~8001, POI variant) for a kiosk that needs no PC.

\textbf{Domain:} a \texttt{RobotBackend} protocol with \texttt{MockRobot}/\texttt{RealRobot} implementations 110 unit tests pass without the physical robot, directly operationalizing principle P5.

\subsection{Edge deployment pattern}

Termux on the tablet runs Python, serves the kiosk over \texttt{0.0.0.0:8001}, connects to \texttt{192.168.20.22:9090}, and triggers TTS via local \texttt{am broadcast}.
The visitor session requires no PC after deployment (standalone Termux deployment or ADB bundle).

\subsection{Conversational layer}
\label{sec:conv}

The vendor \texttt{welcomepatrol} app couples Iflytek TTS via opaque IPC and a proprietary cloud knowledge API. \cybel{} offers an \emph{open, edge-only alternative}, whose scope we state precisely because the title places emphasis on it: the layer below is a validated set of primitives (speak, navigate, answer-from-local-knowledge) rather than a full dialogue system, and LLM-based reasoning over these primitives is future work (Section~\ref{sec:discussion}).

\begin{enumerate}[leftmargin=1.2em]
\item \textbf{Input:} kiosk touch, operator text, or browser Web Speech API (PC only).
\item \textbf{KnowledgeEngine:} keyword scoring over a local JSON knowledge base and FAQ threshold ${\geq}2.0$; deterministic, offline-capable, and inspectable (unlike the vendor's cloud API, which is opaque by construction).
\item \textbf{ReceptionService:} matched answer $\rightarrow$ speech output + optional navigation to a point of interest.
\item \textbf{TourEngine:} ordered stops from a tour definition file, with speech/navigation ordering fixed to relocalize \emph{before} TTS (this ordering bug produced the ``speaks but does not move'' symptom during development, itself a direct instance of the H4 transport/execution gap).
\end{enumerate}

\textbf{LLM extensibility.} A single knowledge-query endpoint accepts the same contract as the local KnowledgeEngine; an LLM backend in the style of~\cite{ahn2022saycan,driess2023paleme} can call the validated \cybel{} navigation/speech primitives without itself rediscovering \rosbridge{} or the TTS bridge this is the concrete sense in which the conversational layer is ``LLM-ready'' rather than already LLM-based.

\subsection{Hybrid navigation case study}
\label{sec:hybrid}

\subsubsection{Coordinate-only strategy (S1)}
Publishing \texttt{/navi\_goal} with coordinates from a JSON knowledge base often failed in the field: robot spoke but \texttt{nav\_status} remained 601 (planner never entered 602), wrong destinations due to map drift, slow relocalization.
Representative trace (session \texttt{tour\_20260623\_142601}): goal published, no 601$\rightarrow$602 transition.

\subsubsection{POI-reuse strategy (S3), testing H3}
The vendor Deployment Tool navigates reliably via named POIs (the chassis localization stack accepts them with vendor-controlled tolerance).
H3 hypothesized that the \cybel{} backend could exploit this by calling \texttt{/tag\_manager/navi} the service \texttt{SelfChassis.sendMoveByMarkerName} identifies in the compiled APK.
The designed flow was:
\begin{enumerate}[leftmargin=1.2em]
\item Create POIs in Deployment Tool (consistent naming convention).
\item Sync \ros{} markers into the \cybel{} POI store (POI-sync module).
\item Kiosk auto-syncs on destination grid load; tour engine references POIs by name.
\item \cybel{} calls \texttt{/tag\_manager/navi} with POI name; monitors \texttt{nav\_status}.
\end{enumerate}
Runtime testing (Section below) showed the service call is silently ignored by the chassis: H3 is rejected.

\subsubsection{Navigation outcomes (S1 vs.\ S3)}

Table~\ref{tab:navcompare} reports outcomes from 5~trials per strategy (same target POI, robot reset to a distant landmark between trials).
S1 achieved $80\%$ (4/5) with mean arrival time $3.5$\,s; the single failure occurred because the robot was mid-navigation during inter-trial reset.
S3 triggered \emph{no} confirmed navigations: two apparent successes (0.5\,s and 0.6\,s) were stale \texttt{nav\_status=603} reads the chassis retains the terminal code of the \emph{previous} navigation until a new goal is accepted.
This result rejects H3 and directly reinforces H4: \texttt{/tag\_manager/navi} is documented at the APK layer but is not a functional navigation trigger on this firmware.

\section{Discussion}
\label{sec:discussion}
%==============================================================================

\subsection{Lessons for closed-robot integration}

\begin{itemize}
\item \textbf{Transport lies (H4):} \rosbridge{} accepts publishes without motor effect; telemetry is ground truth, not the transport acknowledgment.
\item \textbf{Vendor APK as spec (H1):} JADX audit of the vendor's own application accelerated discovery versus generic \ros{} documentation, and is the only channel that revealed implicit preconditions (e.g.\ manual-mode gating).
\item \textbf{Not every plausible channel is real (H2):} a structurally reasonable hypothesis (MQTT as command bus) can be architecturally false; documenting the rejection has value for other integrators of the same vendor family.
\item \textbf{Dual/triple-IP is normal:} document head vs.\ chassis addresses explicitly rather than treating the robot as a single network endpoint.
\item \textbf{APK presence $\neq$ runtime function (H3, rejected):} the \texttt{/tag\_manager/navi} service documented in the vendor APK triggered no navigations at runtime; coordinate-based \texttt{/navi\_goal} (S1) is the reliable path. Runtime validation is non-optional even when the APK source is clear.
\item \textbf{Edge-first is not optional:} closed robot Wi-Fi precludes cloud LLM/TTS dependencies, which shaped every architectural choice in Section~\ref{sec:arch}.
\end{itemize}

\subsection{Generalization: what transfers to other robots}

The four hypotheses transfer beyond this unit. H1 should hold for any vendor robot whose Android companion app is the primary control surface the app must speak the true wire protocol. 
H4 should hold for any robot with a safety or mode-gating layer between its message bus and actuators, common in commercial mobile bases. H2's rejection is vendor-specific: another robot could use MQTT for commands; the value here is the triangulation method (P3) that detects this quickly. 
H3's rejection is itself transferable as a \emph{test}: the methodology found that an APK-documented service was non-functional at runtime this runtime-verification step must be reproduced on every new platform, regardless of how clear the APK source appears. 
What remains vendor-specific: exact topic names, manual-mode gate semantics, POI naming convention, and TTS broadcast contract all rediscoverable via the same seven-phase pipeline.

\subsection{Ethical considerations}

All reverse engineering reported here was performed on hardware owned or lawfully operated by our institution, for interoperability purposes, without redistributing vendor code or bypassing any DRM/licensing mechanism; APK analysis was limited to recovering message schemas, not to extracting or republishing proprietary assets. Principle P4 (non-destructive, no root, no firmware modification) was also an ethical commitment: it keeps the vendor's warranty and update path intact and avoids creating a fork of vendor firmware that could not be maintained. We did not attempt to circumvent the chassis SSH lockout beyond passive discovery of its existence.

\subsection{Limitations}

Chassis shell inaccessible; no native \ros{} TTS; Android~7.1 WebView constraints; DHCP head IP variability; on-robot ASR not yet implemented; the vendor comparison (Table~\ref{tab:compare}) is feature-level, not a controlled user study; guided-tour completion rate and Termux autonomous uptime remain to be measured over extended field sessions.

%==============================================================================
\section{Conclusion}
%==============================================================================

We presented a non-destructive reverse-engineering methodology for closed Android--\ros{} service robots, structured around four falsifiable hypotheses (H1--H4), and validated it end-to-end on the CIOT TY1251D-03195 via \cybel{}, an open edge platform with reconstructed \rosbridge{} protocol, a mock/real SDK, an Android TTS bridge, and a local conversational layer. Two hypotheses were confirmed (H1: APK-as-spec; H4: transport $\neq$ execution) and two were rejected with mechanistic explanations (H2: MQTT is telemetry-only; H3: \texttt{/tag\_manager/navi} non-functional at runtime), each rejection carrying transferable diagnostic value.
The main claim of the paper is methodological: the seven-phase, triangulation-based pipeline and the transport-versus-execution discipline (H4) generalize to other closed Android--\ros{} robots, while the specific protocol details recovered for \cybel{} are this vendor's instantiation of that method.

Future work: a controlled comparison against the vendor application beyond the feature table of Table~\ref{tab:compare}; LLM/RAG reasoning behind the knowledge-query API; on-device ASR; presence-triggered kiosk wake-up; and publication of the exploration scripts as reproducible artifacts for other closed Android--\ros{} robots, to test H1--H4 on a second vendor.
